# ClientBook

客户联系人与商机记录。

需要Python 3.10 或更新版本，包含标准库 sqlite3。

查看命令帮助：

```sh
python3 app.py --help
```

启动本地服务：

```sh
python3 app.py serve --host 127.0.0.1 --port 8080 --data-dir data
```

打开 http://127.0.0.1:8080 查看首页。Ctrl+C 停止服务。`--data-dir` 指定本地业务数据目录，重启时继续使用同一目录。

接口：

- `GET /health` 返回服务状态和产品名称。
- `GET /api/clients` 返回客户列表，首次启动时为空。
- `POST /api/clients/import` 直接接收 CSV 文件内容（请求体即文件字节），返回 JSON 导入报告。
- `POST /api/clients/batch-update` 接收 JSON，对勾选的客户批量修改来源、地区、行业、重要日期。
- 未知路径返回 404，已知路径不支持的方法返回 405。

```sh
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/api/clients
curl -X POST --data-binary @clients.csv http://127.0.0.1:8080/api/clients/import
curl -X POST http://127.0.0.1:8080/api/clients/batch-update \
  -H 'Content-Type: application/json' \
  -d '{"ids":[1,2],"updates":{"industry":{"op":"set","value":" 制造业 "},"important_date":{"op":"clear"}}}'
```

## 批量修改

在首页客户列表中勾选若干客户（支持全选、逐条取消），列表上方会显示当前选中的客户编号、名称与数量；没有勾选客户时无法提交。每条记录以客户编号识别，客户名称和编号不参与编辑，也不会新建客户。

四个可修改字段（`source`、`region`、`industry`、`important_date`）各自独立选择操作：

- `keep`（保持原值，默认）：该字段不修改；初次进入编辑时四个字段均为保持原值，此时输入框为空也不会清空资料，也不会用某个选中客户的内容替其他客户填值。
- `set`（设为填写的值）：填写文本去除前后空白；来源、地区和行业保留内部空白与换行；仅含空白的填写值按清空处理。
- `clear`（清空）：清空后该字段与导入时未填写一样，列表中显示为空，接口返回 `null`。
- `important_date` 设为非空值时，沿用导入规则：须为 `YYYY-MM-DD` 格式的真实日历日期（如闰年 2 月 29 日）。

一次提交中，只要出现以下任一情况，整次请求被拒绝（HTTP 400，返回 `{"error": "具体原因"}`），任何客户都不改变：未选择客户；四个字段全部保持原值；日期无效；设置值不是文本；`updates` 中出现四个字段以外的键；客户编号不是正整数；某个编号找不到对应客户。页面会保留勾选和已填写内容供修正，不显示成功。

`ids` 中重复出现的同一客户编号只视为选中一次；原值已符合本次设置的客户仍计入成功处理数量。

成功时返回去重后的处理数量：

```json
{"updated_count": 2}
```

保存成功后，页面明确显示成功处理的客户数量，刷新列表相关列并清除本次勾选；没有被勾选的客户不受影响。重新打开页面或使用原数据目录重启服务后，仍能看到保存结果。

只有服务以 HTTP 400 返回明确、可读的拒绝原因时，页面才提示整次修改已被拒绝、所有客户资料保持原样，并展示具体原因供修正。其他未取得可靠结论的情况——HTTP 500/502 等非成功状态（即使带有可解析的错误说明）、HTTP 400 却没有可读原因、连接中断、保存回复无法读取或无法解析、成功状态下回复无法解析或缺少有效处理数量——一律提示本次修改是否生效暂时无法确认、客户资料可能已经改变，提醒先核对客户列表再决定是否重新提交；提示保留已知的 HTTP 状态码与可读错误说明，没有可用说明时给出清楚的通用提示，不把空回复或无法解析的内容当成明确拒绝，也不根据旧表格内容推算本次是否成功。此时页面保留结果处理时（而不是提交时）页面上的客户勾选、各字段操作与已填内容：等待期间用户若改选过客户或调整过填写，保留的就是改动后的内容。不执行保存成功后的清理，不自动再次发送修改，旧客户表格继续显示、不清空资料；处理结束后按钮恢复「保存修改」，是否可提交只取决于当前有没有勾选客户，用户核对后主动再次保存时使用当时的选择与填写。

## CSV 导入

在首页选择 CSV 文件并提交后，页面会显示新增数量、未导入数量及逐条原因，列表随即刷新出成功新增的客户；没有客户时仍显示空列表提示。

文件要求 UTF-8 编码（允许开头带 BOM），支持逗号、引号和字段内换行。表头使用 `name`、`source`、`region`、`industry`、`important_date`：

- 只有 `name` 列必须存在，其余列可省略，顺序不限；仅有合法表头时零条新增。
- 缺少 `name` 列、表头重复、出现未知列、编码错误或 CSV 结构损坏时，整份文件拒绝导入（HTTP 400）并说明原因，客户列表保持原样。
- 各字段去掉前后空白；名称必须非空；可选字段省略或为空时视为未填写。
- `important_date` 可以为空，非空时须为 `YYYY-MM-DD` 格式且为真实日历日期。
- 列数不符、缺少名称或日期无效只使该条记录失败，其他有效记录照常新增，报告会说明具体字段及原因。失败记录按原文件的数据记录编号定位（表头不计入编号；带引号字段中的换行仍属于同一条记录）。
- 导入不会更新已有客户。重复判断使用去前后空白后的名称、英文字母不区分大小写（内部空白与标点保持区别）：与已有客户重复时跳过并报告已有客户编号；文件内多条同名有效记录只新增最先出现的一条，后面的记录报告与哪条记录重复。前面记录因字段错误未导入的，不阻止后面同名有效记录新增；重复记录的其他字段即使不同也不会覆盖已保存信息。

成功时（HTTP 200，即使存在失败记录）返回示例：

```json
{
  "imported_count": 1,
  "failed_count": 1,
  "imported": [{"row": 1, "id": 7, "name": "某客户"}],
  "failures": [{"row": 2, "reason": "重要日期无效（2025-13-40）：不是真实日历日期"}]
}
```

文件级错误返回：

```json
{"error": "缺少名称列：表头必须包含 name 列"}
```

只有服务以 HTTP 400 返回明确、可读的拒绝原因时，页面才提示整份文件已拒绝导入、本次没有新增客户、原有客户资料保持原样，并展示具体原因供修正。可读原因可以是回复对象中的非空文本 `error`，也可以是非空的纯文本错误说明，展示时去掉首尾空白，原因中的特殊字符按文字展示。缺少 `name` 表头、UTF-8 编码错误或 CSV 引号结构损坏等文件级错误服务都会返回有效 `error` 原因，仍按此明确提示。

其他拿不到可靠原因的情况——HTTP 400 却是空回复、仅有空白、读取回复失败，或回复能解析成 JSON 但没有合格的 `error`（如 `{"message":"错误"}`、`null`、字符串形式的 JSON），又或 `error` 只有空白、不是文本——一律不能当成明确拒绝：页面保留已知的 HTTP 400，说明没有取得可靠的拒绝原因、本次是否新增客户无法确认、客户资料可能已经改变，提醒先核对客户列表再决定是否重新导入；不展示原始 JSON，不显示新增数量或零新增，也不声称已经回滚或整份文件已拒绝。HTTP 500/502 等其他非成功状态（即使带有可解析的错误说明）与连接中断同样按无法确认处理。无法确认时已选文件与当前客户表格保留：不清空客户、不切换为空列表，不触发导入后的列表读取，也不自动重新提交；处理结束后导入按钮恢复可用。正常导入、合法零新增，以及重复客户或字段错误造成的部分未导入，仍按完整有效报告显示数量与逐条原因；已确认的导入结果与随后客户列表读取的结果分别提示。

`GET /api/clients` 仍保持 `{"clients": [...]}` 外层结构，每条记录含 `id`、`name` 以及 `source`、`region`、`industry`、`important_date`，升级前已有的旧客户这些新增字段为空。

## 测试

接口冒烟测试会启动真实服务（临时数据目录，结束后自动清理），覆盖导入、批量修改与路由的公开行为：

```sh
python3 smoke_test.py
```

首页批量保存的页面层面回归测试（`page_test.mjs`）同样启动真实 `app.py`，再用 Puppeteer 驱动系统 Chrome 打开首页，通过请求拦截分别破坏「保存成功之后的那次列表读取」，验证保存结果与随后读取客户列表的结果分别处理：

- 保存回复确认成功后，即使紧接着的列表读取连接失败、返回非成功状态、内容无法解析或缺少客户数组，页面仍按保存回复的 `updated_count` 明确显示成功处理数量（不按刷新后的记录数重算），并提示列表暂未更新、当前资料可能仍是保存前内容、稍后刷新即可、无需再次保存；
- 保存成功后无论列表是否读到，勾选清除、已选归零，四个字段恢复「保持原值」、输入清空并回到不可填写状态；读取失败时旧表格保留、不显示空列表提示、不重发保存请求，按钮结束等待且无勾选时不可提交；
- 之后刷新或重新打开页面读取成功时显示真实资料并撤下失败提示；真实空列表正常显示空列表提示；
- 保存成功且列表读取成功的正常路径，以及保存被明确拒绝（400 且有可读原因）时保留勾选与已填内容、不套用成功后清理的路径，同样在覆盖范围内；
- 保存请求没有可靠结论时（HTTP 500/502 即使带可解析错误说明、503 纯文本、空回复、无法解析内容、JSON 无错误说明、HTTP 400 无可用原因、成功状态但回复无法解析或缺少有效处理数量、保存请求连接中断）：页面一律提示本次修改是否生效无法确认并要求先核对客户列表再决定是否重新保存，保留已知状态码与可读说明、无说明时给通用提示，不显示成功数量、不声称资料保持原样或已经回滚；勾选、字段操作与已填内容保留、旧表保留且不触发保存后的列表刷新、不自动重发，按钮恢复后能否提交只取决于当前勾选；用户核对后主动再次保存使用当时的选择与填写；等待期间改选客户或调整填写后遇到 500 时，保留的是结果处理时页面上的内容，不恢复提交时的旧选择；
- 保存请求尚未返回的等待期间：按钮保持「正在保存…」不可提交，选中信息、字段操作与填写保留且不显示成功数量；重复提交（含回车触发的表单提交）不发出第二个请求、等待提示不被替换成成功或未选客户错误；期间可正常改选客户、调整字段与输入，但不解除等待状态（含先取消全部勾选再重新选择）；已发出请求的勾选客户与修改内容以第一次保存时为准，结果返回后不自动补交等待期间的改动，后来勾选的客户不被更新、后来输入的值不替换已提交的值；等待期间改动后被服务以 400 拒绝时，保留的是返回结果时页面上的勾选、字段操作与填写，等待结束后有选中客户才能再次保存。
- 字段「最终操作选择」的回归（场景 L）：保存只以每个字段最后选定的「保持原值」「设为填写的值」「清空」为准，输入框残留文字、变成不可填写状态或留空都不能自行替代这个选择——
  - 先选「设为填写的值」并输入文字、再改回「保持原值」，随后改另一个字段保存：前一字段每名客户分别保留自己的原值，残留文字既不写入也不因输入框禁用而清空；重要日期先填无效日期（如 2023-02-29）再改保持原值时，不校验该残留日期，也不妨碍其他字段的有效修改成功；
  - 最终选择「清空」时，即使之前留下文字或无效日期，保存后该字段为未填写、接口返回 `null`，不再校验残留内容；
  - 最终选择「设为填写的值」但输入为空或只含空格、制表符、换行时，四个字段都按清空处理；来源、地区、行业仅填空白与明确清空结果相同，重要日期仅填空格也清空、不报日期格式错误；保存后列表显示未填写；非空文本仍只去前后空白，内部空白与换行保留；客户名称、编号与未选中客户不变，原本为空的字段不会从其他选中客户补入内容；
  - 拒绝同样受到保护：四个字段最终全部保持原值（即使输入框留有文字或无效日期）也拒绝保存并说明没有修改项，不显示成功数量；重要日期最终选择设置且填写无效日期时整次修改拒绝、其他字段不先保存；拒绝后保留当前勾选、字段操作与填写供修正，有效保存则按实际选中客户数显示成功、更新相关列并清除勾选，四个字段恢复保持原值、输入清空并回到不可填写状态。

接口冒烟测试 `smoke_test.py` 对同一组「最终操作选择」规则在 HTTP 接口层另有直接覆盖（`keep` 说明中的残留值被忽略、纯空白 `set` 与 `clear` 均落库为 `null`、全部 `keep` 拒绝、日期无效的原子拒绝等），与页面层面回归互相印证。

接口冒烟测试还直接覆盖批量修改的另外两类整次拒绝规则：`updates` 中混入 `name`、`id` 或不存在的字段（即使该字段选择 `keep`，也无论非法项排在合法项之前还是之后），以及四个可修改字段的 `set` 设置值为数字、布尔、null、数组、对象或缺少 `value` 时，均返回 HTTP 400 与非空文本原因（指出哪个字段不能修改、或指出设置值不是文本），响应不含 `updated_count`；每次拒绝后都重新读取客户列表逐客户核对编号、名称与四个可修改字段保持原值（原本为空的仍为空），未选中客户与客户总数不受影响，同次请求中的合法修改项也不会先保存。只修正掉不合法项后再次提交同样的合法修改，仍按现有规则成功并返回实际处理数量。

接口冒烟测试还直接覆盖客户选择编号的校验回归：`ids` 数组混入数字形式的文本（即使内容恰好等于已有编号）、浮点数（包括写成 `1.0` 或恰为某编号整数值的浮点）、布尔值（不能被当成编号 1 或 0）、null、零与负数时，无论不合格值排在合法编号之前还是之后，即使同次请求带有可正常执行的设置与清空，整次请求都返回 HTTP 400 与非空可读原因（说明客户编号必须为正整数），响应不含 `updated_count`，也不表示部分客户已修改；每次拒绝后重新读取客户列表，逐客户核对来源、地区、行业与重要日期分别保持自己的原值（原本为空的仍为空），资料互不相同的客户不会被统一成其中一人的内容，客户编号、名称、客户总数与未选中客户均不变。空编号数组拒绝并说明未选择客户；`ids` 缺失或为 null、文本、数字、对象（不是数组）时拒绝并说明需要客户编号数组，同样整次不写入。把不合格值移除、只保留实际存在的整数编号后，同样的合法字段修改正常成功并只影响明确要求设置/清空的字段（未要求的字段各自保留原值），重复出现的合法编号仍只计一名客户，保持现有的成功数量、错误回复与空值含义。

针对一次提交涉及较多客户（名单超过 SQLite 单条语句参数数量限制）的自动回归由 `long_list_test.py` 承担，它与冒烟测试一样启动真实服务、只调用公开的 CSV 导入、客户列表与批量修改接口，不模拟任何服务端行为：

```sh
python3 long_list_test.py
```

- 长名单一次保存成功（不拆成需要用户分别确认的多次修改）：设置来源、清空行业，地区与重要日期保持原值；成功回复 `updated_count` 为去重后的 1200——同一编号在名单首、尾等不同位置重复出现也只计一次，原值已符合设置内容的客户仍计入数量；逐客户核对名单末尾的客户也完成设置/清空且保留自己的地区与日期，保持原值的字段确实逐人保留、未被统一，原本未填写的字段仍为空（不会从其他客户补入内容）；来源只去前后空白、内部空白与换行保留，行业清空后列表接口返回 `null`；未选中客户、客户名称、编号与客户总数保持原样；四个字段同时操作（设置来源/地区/日期、清空行业，赋值参数同样参与分块）的长名单也在覆盖范围内；
- 长名单混入一个找不到的客户编号时（分别覆盖缺失编号位于名单末尾——前面编号全部有效——以及位于名单中部且同时含重复编号），即使字段修改合法，仍整次返回 HTTP 400 与指出缺失编号的可读原因、不返回处理数量；重新读取列表逐客户核对所有客户保持提交前的资料，名单前面的客户没有先发生改变；去掉不存在的编号后同一批修改一次成功；
- 保存已经开始、尚未全部完成时数据库出错：测试启动器在第 3 个更新分块执行时、以及在所有分块执行成功但事务提交时各注入一次真实的 `sqlite3` 磁盘 I/O 错误，两种情况都必须返回 HTTP 400 与可读的保存失败说明、不返回处理数量；失败后重新读取客户列表确认本次任何客户都没有留下修改、无部分保存，重启后端打开同一数据库后仍无半截保存，随后同一批修改一次提交即可完整成功。

首页 CSV 导入结果展示的页面层面回归测试（`import_page_test.mjs`）同样启动真实 `app.py`，再用 Puppeteer 通过真实文件选择框上传 CSV，并通过请求拦截分别改写「导入响应」与「导入成功之后的那次列表读取」，验证可靠报告与无法确认的结果分别处理：

- 服务返回完整有效报告时，严格按报告显示新增数量与未导入数量，按原文件数据记录编号（表头不计入；带引号字段里的换行不拆成多条记录）逐条展示未导入原因；覆盖有效与无效记录混在同一文件的部分成功、只有表头的合法零新增、以及全部因重复或字段问题跳过（仍显示完整数量与原因，不说成整份文件被拒绝）；
- 即使请求返回成功状态：回复无法解析、数量不是非负整数（负数、小数、文本、布尔、缺失）、未导入明细缺失或不是数组、明细条数与未导入数量不符、记录编号不是正整数或原因不是非空文本时，页面显示结果无法确认，提示先核对客户列表再决定是否重新导入；不显示成功数量，不补造零新增/空明细，也不凭客户列表行数推算新增数量，页面不出现 undefined/NaN；
- 已取得有效报告后，随后的列表读取连接失败、返回非成功状态、内容无法解析或缺少客户数组，都不改变已确认的数量与逐条原因：附加「列表暂未更新、资料可能不是最新、稍后刷新即可、无需重新导入」的提示，此前显示的客户行保留、不清空、不显示空列表提示；重新打开页面读取成功后显示实际保存的资料；
- 结果处理结束后导入按钮恢复可用、已选文件保留、不会自动再次提交；正常导入并成功刷新列表的路径，以及整份文件被明确拒绝（HTTP 400，真实结构损坏文件）时原有错误说明与资料不变的行为同样在覆盖范围内。
- HTTP 400 的两类结果分别处理：只有拿到明确、可读的拒绝原因（回复对象的非空文本 `error`，或非空的纯文本错误说明，展示去首尾空白）时才提示整份文件已拒绝、本次没有新增客户、原有资料保持原样并展示原因，原因中的特殊字符按文字展示（覆盖 JSON `error`、纯文本、特殊字符转义）；缺少 `name` 表头、UTF-8 编码错误、引号结构损坏（`bad2.csv` 同类）等真实文件级错误仍属此类；
- HTTP 400 却没有可靠原因时——空回复、仅含空白、读取回复失败（状态码可读但响应体读取抛错）、能解析成 JSON 但没有合格 `error`（`{"message":"错误"}`、`null`、字符串形式的 JSON、数字/数组）、`error` 只有空白或不是文本（数字、布尔、null）——按无法确认处理：保留已知 HTTP 400 与「没有可靠拒绝原因」说明、客户资料可能已经改变，不显示新增数量或零新增、不声称回滚或整份文件已拒绝、不展示原始 JSON；已选文件与旧客户行保留、不触发导入后的列表读取、不自动重发，按钮恢复可用。
